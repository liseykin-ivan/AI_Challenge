# Промт: публикация в репозиторий

Опубликуй изменения проекта AI Challenge в GitHub (`liseykin-ivan/AI_Challenge`).
Коммит и ветка создаются git'ом в папке проекта, затем обычный `git push`.

Режимы:
- **Публикация дня** — по умолчанию, когда просят опубликовать день или результаты задания.
  Коммит в `main` и ветка `day_<N>` на том же коммите; обе ветки отправляются одной атомарной
  операцией (уходят вместе или не уходят вовсе). N — сквозной номер дня челленджа: самый большой номер
  среди `tasks/day_<N>.md`, если пользователь не назвал другой.
- Старые ветки `week_<W>/day_<D>` (дни 1–6) не трогай — на них ссылаются внешние ресурсы. У каждой есть
  дубликат `day_1` … `day_6` на том же коммите. Новые ветки создаются только в формате `day_<N>`.
- **Обновление** — правка вне дня (инструменты, README, промпты): коммит только в `main`, без ветки дня.

## Мультиагентный режим

Публикация — строго последовательная операция: `git add`, `git commit` и `git push` выполняет один
агент, распараллеливать их нельзя. Перед работой прочитай `MODELS.md`, разделы 4–5.

- Параллельно можно запускать только независимые проверки: секреты в диффе, состав коммита, наличие
  результатов и раздела README, состояние веток. Их могут делать разные субагенты на
  `deepseek-v4.1-flash` или `glm-5.3-flash`.
- Один файл — один писатель; не давай двум агентам исправлять один и тот же файл.
- Если проверка нашла проблему — остановись по правилу ниже, не позволяй второму агенту «исправить»
  то же самое.
- В конце отчёта перечисли, какие проверки шли параллельно, а какие последовательно.

Если какая-то проверка ниже не прошла — остановись, ничего не обходи и не исправляй силой,
сообщи пользователю причину и спроси, что делать.

## 1. Подготовка и проверки

1. Состояние репозитория:
   - текущая ветка — `main`;
   - нет незавершённого merge/rebase/cherry-pick (`MERGE_HEAD`, `rebase-merge`, `rebase-apply`, `CHERRY_PICK_HEAD` в `.git`);
   - в `.git` нет `*.lock` (поиск по всей `.git`). Если есть — сообщи их время создания и спроси, удалить ли.
2. `git fetch origin`. `origin/main` должен уже входить в историю локального `main`
   (`git merge-base --is-ancestor origin/main main`). Если локальный `main` отстал или разошёлся с GitHub —
   остановись и сообщи.
3. Для публикации дня: ветки `day_<N>` нет ни локально, ни на GitHub (`git ls-remote --heads origin <ветка>`).
   Если она уже есть — день, скорее всего, уже опубликован: сообщи и ничего не делай.
4. Для публикации дня проверь, что результаты на месте: код, файл задания (`tasks/day_<N>.md`), отчёты прогонов
   и выводы в `results/`, раздел дня в README (и ссылка на выводы).
5. Удали из папки проекта временные файлы (бандлы, тестовые копии, черновики) — в коммит попадёт всё,
   что не исключено `.gitignore`.
6. `git add -A`, затем проверь, что войдёт в коммит (`git diff --cached --stat`):
   - есть что коммитить;
   - нет `.env`, `.venv/`, `__pycache__/`, `*.bundle` и файлов больше 20 МБ;
   - в изменениях (`git diff --cached`) нет значений ключей из `.env` (переменные с KEY/TOKEN/SECRET в имени).
     Сверяй программно и сами ключи не выводи.
   Покажи пользователю список файлов. Если в нём есть лишнее — остановись.
7. Сообщение коммита запиши в файл **вне** папки проекта, в стиле прошлых дней:
   первая строка `День <N>: <что сделано>`, где N — сквозной номер дня (для обновления — коротко, что изменено),
   пустая строка,
   2–5 строк о содержимом, затем строки атрибуции (Co-Authored-By и др.), если они заданы в сессии.
8. `git commit -F <файл>`. Если `user.name`/`user.email` не настроены, возьми их из последнего коммита
   (`git -c user.name=... -c user.email=... commit`).
9. Для публикации дня: `git branch day_<N>` — на только что созданном коммите.

## 2. Отправка

1. Отправь одной атомарной операцией:
   `git push --atomic origin main [day_<N>]`.
   Если push отклонён — остановись и сообщи ответ GitHub; ничего не форсируй (`--force` не использовать).
2. `git ls-remote origin` — `main` (и ветка дня) на GitHub указывают на новый коммит.

## 3. Завершение

1. Удали файл сообщения коммита.
2. `git fetch origin`; для ветки дня — `git branch -u origin/day_<N> day_<N>`.
3. `git status -sb` показывает `main...origin/main` без «ahead/behind», в `.git` нет `*.lock`.

В конце сообщи хеш коммита и название ветки (для обновления — только хеш).
