# AI Challenge — CLI-чат с LLM

День 1 (`main.py`): консольное приложение отправляет запрос в OpenCode Go (OpenAI-совместимый API)
через голый `httpx` и печатает ответ, модель, токены и время.
День 2 (`day2_format.py`): сравнение способов управлять форматом ответа — см. [ниже](#день-2-формат-ответа).
День 3 (`day3_reasoning.py`): 4 способа рассуждения × 2 уровня reasoning — см. [ниже](#день-3-разные-способы-рассуждения).
День 4 (`day4_temperature.py`): один запрос при temperature 0 / 0.7 / 1.2 — см. [ниже](#день-4-температура).
День 5 (`day5_models.py`): одни и те же задачи на маленькой, средней и флагманской модели — см. [ниже](#день-5-версии-моделей).
День 6 (`day6_agent.py`): первый агент — сам вызывает инструменты в цикле — см. [ниже](#день-6-первый-агент).
День 7 (`day7_memory.py`): агент из Дня 6 сохраняет историю в JSON и продолжает диалог после перезапуска — см. [ниже](#день-7-сохранение-контекста).
День 8 (`day8_tokens.py`): агент из Дня 7 считает токены, стоимость и заполнение контекстного окна — см. [ниже](#день-8-работа-с-токенами).
День 9 (`day9_compression.py`): агент из Дня 8 заменяет старую часть истории на summary и экономит токены — см. [ниже](#день-9-сжатие-истории).

## Установка (PowerShell, Python 3.11+)

```powershell
cd C:\Users\user\Desktop\AI_Projects\AI_Challenge
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
notepad .env   # впишите OPENCODE_API_KEY
```

Если `Activate.ps1` запрещён политикой: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

## Запуск

```powershell
python main.py "Привет, кто ты?"
python main.py                              # спросит запрос в консоли
python main.py --model <id> "Привет"        # другая модель (id — из списка ниже)
```

Пример вывода:

```
Привет! Я — ИИ-ассистент...

deepseek-v4.1-flash | токены: 31/24 | 1.42 с
```

При ошибке печатается понятное сообщение, код выхода — 1.

Временные сбои `LLMClient` повторяет сам, во всех днях: таймаут, обрыв связи, HTTP 408/409/425/429 и любой 5xx.
По умолчанию до 2 повторов (`LLM_RETRIES` в `.env`, `0` — без повторов) с паузой ~1 с, ~2 с (±25%, не больше 30 с)
или столько, сколько просит заголовок `Retry-After`. Ошибки самого запроса — 400, 401, 404, переполнение окна —
не повторяются: ответ был бы тем же. Если не помогли и повторы, ошибка сообщает число попыток.
`ChatResult.attempts` — сколько попыток понадобилось, `LLMClient.stats` — запросы, повторы и отказы клиента.
Учтите, что запрос, оборванный по таймауту, провайдер мог успеть выполнить и посчитать.

## Проверка доступа без кода

```powershell
$key = ((Get-Content .env) -match '^OPENCODE_API_KEY=')[0].Split('=', 2)[1]
$h = @{ Authorization = "Bearer $key"; "User-Agent" = "ai-challenge-cli/0.1"
        "x-opencode-session" = [guid]::NewGuid().ToString("N") }   # без него OpenCode Go отвечает 400

# список моделей
(Invoke-RestMethod https://opencode.ai/inference/go/v1/models -Headers $h).data.id

# тестовый запрос
$body = '{"model":"deepseek-v4.1-flash","messages":[{"role":"user","content":"ping"}]}'
(Invoke-RestMethod https://opencode.ai/inference/go/openai/v1/chat/completions `
  -Method Post -Headers $h -ContentType "application/json" -Body $body).choices[0].message.content
```

## День 2: формат ответа

`day2_format.py` отправляет один и тот же запрос с разным уровнем контроля
и проверяет, может ли код распарсить ответ.

```powershell
python day2_format.py                        # все 7 вариантов × 3 прогона
python day2_format.py --runs 5 --max-tokens 40
python day2_format.py --variants format,schema --runs 2
python day2_format.py --timeout 120 --temperature 0.7 --model <id>
```

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `--runs` | 3 | прогонов на каждый вариант |
| `--variants` | все | список через запятую из таблицы ниже |
| `--max-tokens` | 60 | лимит для `max_tokens` и `schema_max_tokens` |
| `--timeout` | `LLM_TIMEOUT` из `.env` | таймаут одного запроса, с |
| `--temperature` | как у модели | температура для всех вариантов |
| `--model` | `LLM_MODEL` из `.env` | id модели |

| Вариант | Что меняется в запросе |
|---|---|
| `plain` | только вопрос, без системного промта |
| `format` | формат JSON описан словами в системном промте |
| `max_tokens` | `format` + `max_tokens` (по умолчанию 60) |
| `stop` | `format` + просьба закончить маркером `<END>` + `stop=["<END>"]` |
| `json_mode` | `format` + `response_format={"type": "json_object"}` |
| `schema` | `format` + `response_format` со строгой JSON Schema (`strict: true`) |
| `schema_max_tokens` | строгая схема + `max_tokens` |

Каждый ответ проверяется тремя способами: `json.loads` как есть, JSON после чистки
(срезать ```-обёртку и текст вокруг `{...}`) и соответствие схеме (поля, типы, ровно 3 языка).
Для каждого прогона печатаются токены (сколько из них ушло на скрытое рассуждение),
время и `finish_reason`, а для сломанных ответов — причина: например, «лимит max_tokens
съело рассуждение» или «обрезан по лимиту». В конце — итоговая таблица по вариантам.
В `results/` пишутся сырые ответы вместе с рассуждением (`.json`) и отчёт (`.md`),
где для пустого ответа показан хвост рассуждения.
Если провайдер не поддерживает `response_format` или запрос упал по таймауту,
вариант покажет ошибку API, а не уронит скрипт.

Выводы по прогонам на `deepseek-v4.1-flash` — в [`results/day2_conclusions.md`](results/day2_conclusions.md).

## День 3: разные способы рассуждения

`day3_reasoning.py` решает 10 задач с известным ответом (логика, алгоритмы, анализ)
четырьмя способами при минимальном и максимальном рассуждении, проверяет ответы кодом
и строит таблицу «способ × рассуждение → верных / токены / время».

```powershell
python day3_reasoning.py --probe             # сначала: как у модели включается/выключается рассуждение
python day3_reasoning.py                     # полный прогон: 10 × 4 × 2 = 80 решений (~100 запросов)
python day3_reasoning.py --runs 3            # по 3 прогона — устойчивее к случайности
python day3_reasoning.py --set easy          # первый, лёгкий набор задач
python day3_reasoning.py --tasks dice,josephus --methods direct,experts --levels low
python day3_reasoning.py --low reasoning_effort=low --high reasoning_effort=high
python day3_reasoning.py --low thinking.type=disabled --high thinking.type=enabled
```

| Способ | Что в запросе |
|---|---|
| `direct` | только условие |
| `steps` | условие + «Решай пошагово.» |
| `meta` | 1-й запрос: «составь промпт для решения задачи»; 2-й — решение по этому промпту |
| `experts` | аналитик, инженер и критик решают по очереди, у каждого свой ответ, затем итог |

**Наборы задач.** `easy` — первый набор (сёстры Алисы, угол в 3:15, нули в 2026! и т. п.):
`deepseek-v4.1-flash` решил его на 9–10 из 10 при любой настройке, и способы почти не различались.
`hard` (по умолчанию) — задачи, где ответ нельзя вспомнить, а надо считать, перебирать
или замечать ловушку: прямые углы стрелок за сутки, буквы во фразе, рыцари и лжецы вчетвером,
день недели 29.02.2032, пятницы 13-е в 2027, условная вероятность на костях, 7^2026 mod 100,
пятизначные числа с суммой цифр 9, делители 2026², задача Иосифа Флавия.
Эталоны всех задач проверены кодом.

Во всех способах к условию добавлена одна и та же строка формата `ОТВЕТ: <...>`,
чтобы ответ проверялся кодом (числа, день недели, рыцари/лжецы — с нормализацией).

**Уровни рассуждения.** Какой параметр понимает модель, у OpenAI-совместимых провайдеров
разнится, поэтому скрипт сначала делает пробу: шлёт одну задачу с вариантами
`reasoning_effort` (none/minimal/low/high/max), `reasoning.effort`, `thinking`
и смотрит `reasoning_tokens` в ответе. Минимальным уровнем становится вариант с самым
коротким рассуждением, максимальным — с самым длинным. Проба кэшируется
в `results/day3_probe.json` (`--reprobe` — повторить), её выбор можно переопределить `--low/--high`
(форма `ключ=значение`, вложенные — через точку; JSON тоже принимается, но PowerShell 5 съедает в нём кавычки).

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `--set` | `hard` | набор задач: `hard` или `easy` |
| `--runs` | 1 | прогонов каждой пары задача × способ |
| `--workers` | 4 | параллельных запросов |
| `--timeout` | 300 | таймаут запроса, с (высокое рассуждение отвечает долго) |
| `--tasks`, `--methods`, `--levels` | все | подмножество через запятую |
| `--model` | `LLM_MODEL` из `.env` | id модели |

Токены в таблице — prompt + completion по всем запросам способа (у `meta` их два),
отдельно показано, сколько ушло на рассуждение. Время — сумма времени ответов модели.
Результаты: `results/day3_<набор>_<время>.json` (все ответы, рассуждения и сгенерированные промпты)
и `results/day3_<набор>_<время>.md` (таблица, разбивка по задачам и экспертам, ошибки).

Выводы по прогону на `deepseek-v4.1-flash` — в [`results/day3_conclusions.md`](results/day3_conclusions.md).

## День 4: температура

`day4_temperature.py` отправляет одни и те же запросы с `temperature` = 0, 0.7 и 1.2,
каждую комбинацию — 5 раз, проверяет ответы кодом и считает, насколько они расходятся между прогонами.

```powershell
python day4_temperature.py                          # 4 задачи × 3 температуры × 5 прогонов = 60 запросов
python day4_temperature.py --runs 10                # больше прогонов
python day4_temperature.py --temps 0,0.7,1.2,1.8    # другие температуры
python day4_temperature.py --tasks letters,names    # часть задач
python day4_temperature.py --reasoning model        # не выключать рассуждение
python day4_temperature.py --recheck results\day4_<время>.json   # перепроверить сохранённые ответы без запросов
```

| Задача | Тип | Что проверяется |
|---|---|---|
| `letters` | один ответ | сколько раз «а» во фразе «Карл у Клары украл кораллы…» (эталон 12); ответ — строго `{"answer": <целое>}` |
| `days` | один ответ | дней от 01.01.2026 до 01.03.2028 (эталон 790); тот же JSON-формат |
| `names` | генерация | 5 названий кофейни у моря — чистый JSON-массив ровно из 5 строк, без повторов, ≤ 4 слов, каждое только кириллицей |
| `slogan` | генерация | слоган — одна строка, ≤ 8 слов, без кавычек, по-русски |

Эталоны посчитаны кодом. В задачах с одним ответом «формат сломан» и «неверный ответ» считаются
отдельно: число достаётся из ответа мягко, даже если JSON обёрнут в ```` ``` ```` или вокруг есть текст.

Для каждой пары «задача × температура» скрипт печатает и пишет в отчёт:
сколько **разных** ответов из 5 (после нормализации пробелов и регистра), среднюю попарную
**похожесть** текстов (difflib, 100% — все одинаковые), сколько раз **сломался формат**,
сколько **неверных** ответов, для названий — сколько **уникальных** названий набралось за все прогоны
и сколько повторилось в каждом. Отдельной строкой — дал ли `temperature = 0` посимвольно одинаковый ответ.

По умолчанию рассуждение выключено (`reasoning_effort: "none"`): у reasoning-моделей температура может
не влиять на скрытое рассуждение, и сравнение было бы нечистым. `--reasoning model` — не передавать параметр.

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `--temps` | `0,0.7,1.2` | температуры через запятую |
| `--runs` | 5 | прогонов каждой комбинации |
| `--tasks` | все | `letters,days,names,slogan` |
| `--reasoning` | `none` | `none` — выключить рассуждение, `model` — как у модели по умолчанию |
| `--workers` | 4 | параллельных запросов |
| `--timeout` | 120 | таймаут запроса, с |
| `--model` | `LLM_MODEL` из `.env` | id модели |
| `--recheck` | — | без запросов к модели: заново проверить ответы из сохранённого `.json` и перезаписать его и `.md` |

Результаты: `results/day4_<время>.json` (все ответы, токены, проверки) и `results/day4_<время>.md`
(сводная таблица, автоматические наблюдения и все ответы по каждой температуре — это и есть примеры).

Выводы по прогону на `deepseek-v4.1-flash` — в [`results/day4_conclusions.md`](results/day4_conclusions.md).

## День 5: версии моделей

`day5_models.py` решает 10 задач набора hard из Дня 3 (те же эталоны и та же проверка ответа кодом)
на трёх моделях одного семейства из подписки OpenCode Go и сравнивает точность, время, токены и стоимость.

| Уровень | Модель | Вход / выход, $ за 1M токенов |
|---|---|---|
| маленькая | `qwen3.8-flash` | 0.15 / 0.47 |
| средняя | `qwen3.7-plus` | 0.40 / 1.60 |
| флагман | `qwen3.8-max` | 2.00 / 6.00 |

```powershell
python day5_models.py --probe                # доступны ли модели и выключается ли у них рассуждение (6 запросов)
python day5_models.py                        # 10 задач × 3 модели × 3 прогона = 90 запросов, рассуждение выключено
python day5_models.py --reasoning model      # рассуждение как у модели по умолчанию
python day5_models.py --method steps         # к условию добавить «Решай пошагово.»
python day5_models.py --models glm-5.3-flash,glm-5.3   # другие модели (цены — в словаре PRICES)
python day5_models.py --recheck results\day5_<время>.json   # пересчитать отчёт по сохранённым ответам
```

| Параметр | По умолчанию | Что делает |
|---|---|---|
| `--models` | `qwen3.8-flash,qwen3.7-plus,qwen3.8-max` | id моделей от маленькой к флагману |
| `--runs` | 3 | прогонов каждой пары модель × задача |
| `--reasoning` | `off` | `off` — `reasoning_effort: "none"`, `model` — как у модели по умолчанию |
| `--method` | `direct` | `direct` — только условие, `steps` — плюс «Решай пошагово.» |
| `--tasks` | все | подмножество задач через запятую |
| `--workers` | 6 | параллельных запросов; модели в очереди чередуются, чтобы нагрузка у провайдера была для всех одинаковой |
| `--timeout` | 300 | таймаут запроса, с |

Для каждого запроса записываются время, токены (вход, выход, рассуждение, кэш) и стоимость по прайсу
OpenCode Go. Скрипт сверяет её с `usage.opencode.list_cost` из ответа и отдельно показывает `allowance` —
сколько списано из лимита подписки. Время в сводке — медиана и p90 по отдельным запросам:
часть запросов висит в очереди у провайдера по 2–3 минуты, и сумма времени из-за них ничего не говорит.
В отчёте: таблица «модель → верных / время / токены / стоимость», сравнение «флагман против маленькой»
(во сколько раз дороже, на сколько п. п. точнее, цена дополнительного верного ответа), разбивка по задачам,
список задач, где маленькой модели хватило во всех прогонах, и все неверные ответы.
Результаты: `results/day5_<время>.json` (все ответы и usage) и `results/day5_<время>.md`.

Выводы по двум прогонам (рассуждение выключено и включено) — в [`results/day5_conclusions.md`](results/day5_conclusions.md).

## День 6: первый агент

`day6_agent.py` — агент как отдельная сущность: класс `Agent` хранит историю диалога и набор инструментов,
а метод `run(запрос)` крутит цикл «запрос к модели → вызов инструментов → результат обратно в модель → …»,
пока модель не ответит без вызова инструментов. Инструменты описаны JSON-схемой в поле `tools` запроса
(OpenAI-совместимый function calling); модель сама выбирает инструмент и аргументы, код агента выполняет вызов
и кладёт результат в историю сообщением `role: "tool"`. Интерфейс от агента отделён: шаги цикла агент отдаёт
в колбэк `on_event`, а CLI их печатает.

| Инструмент | Что делает |
|---|---|
| `get_current_time(timezone)` | текущие дата, время и день недели в часовом поясе IANA (`zoneinfo`) |
| `calculator(expression)` | арифметика `+ - * / // % **` — разбор через `ast`, без `eval` |
| `convert_currency(amount, from_currency, to_currency)` | перевод по курсу, зашитому в `RATES_RUB` (RUB, USD, EUR, CNY, GBP, JPY) |

```powershell
pip install -r requirements.txt              # добавился tzdata: на Windows без него zoneinfo не знает часовых поясов
python day6_agent.py                         # чат в консоли; команды /tools, /reset, /exit
python day6_agent.py "Который час в Токио?"  # один запрос и выход
python day6_agent.py --demo                  # три проверочных сценария + отчёт в results/
python day6_agent.py --model <id> --demo     # другая модель (должна поддерживать tools)
```

Проверочные сценарии (`--demo`), каждый — с чистой историей:

| Сценарий | Запрос | Что проверяется |
|---|---|---|
| без инструментов | «Объясни в двух предложениях, чем LLM-агент отличается от одного вызова модели.» | инструменты не вызваны |
| один инструмент | «Который час сейчас в Токио?» | вызван `get_current_time` |
| два инструмента подряд | «Сколько рублей я заплачу за покупку на 150 долларов, если банк сверху берёт комиссию 3,5%?» | вызваны `convert_currency` и `calculator` в двух разных шагах: второй вызов использует результат первого |

Каждый шаг печатается в консоль: запрос к модели (токены, время) и вызов инструмента с аргументами и результатом.
Ошибки инструментов (неизвестный инструмент, битый JSON аргументов, недопустимое выражение) не роняют агента,
а возвращаются модели как результат вызова. Цикл ограничен `--max-steps` (8) запросами к модели за ход;
если запрос к API падает посреди цикла, история откатывается к состоянию до хода.
Результаты `--demo`: `results/day6_<время>.md` (таблица и трасса вызовов) и `results/day6_<время>.json` (вся история сообщений).

Выводы по двум прогонам на `deepseek-v4.1-flash` (оба — 3/3 сценария) — в [`results/day6_conclusions.md`](results/day6_conclusions.md).

## День 7: сохранение контекста

`day7_memory.py` — агент из Дня 6 (тот же класс `Agent`, те же инструменты), который хранит историю диалога
в JSON-файле и при запуске загружает её обратно. `PersistentAgent` наследует `Agent` и добавляет к нему
`HistoryStore` — файл `memory/<сессия>.json`.

В файл пишется весь список `messages` в том виде, в каком он уходит в API: `system`, `user`,
`assistant` с `tool_calls` (и `reasoning_content`, если модель его отдаёт), `role: "tool"` с результатами
инструментов. После перезапуска модель получает тот же контекст, что и до выключения, поэтому помнит
и реплики, и результаты прошлых вызовов. Вместе с историей сохраняется `session_id` (заголовок `x-opencode-session`):
для OpenCode Go это продолжение того же диалога. Отдельно, без отправки в API, хранится статистика по ходам
(время, токены, число вызовов).

```powershell
python day7_memory.py                          # чат; история сессии default подхватывается сама
python day7_memory.py --session work           # другая сессия — другой файл memory/work.json
python day7_memory.py "А сколько это в евро?"  # один ход с памятью и выход
python day7_memory.py --new                    # начать заново (старая история уходит в архив)
python day7_memory.py --demo                   # 3 запуска в отдельных процессах + отчёт в results/
```

Команды чата: `/history` — весь диалог с вызовами инструментов и их результатами, `/tools`,
`/reset` — очистить (старый файл переименовывается в `<сессия>_<время>.json`, а не удаляется), `/exit`.
При запуске агент пишет, сколько сообщений, ходов и результатов инструментов восстановлено,
и показывает последний обмен.

Надёжность:
- история сохраняется после каждого завершённого хода, атомарно (временный файл + `os.replace`):
  если процесс убит посреди записи, в файле остаётся прошлая версия;
- если запрос к API упал или ход прерван Ctrl+C, история откатывается к состоянию до хода, файл не меняется;
- при загрузке незавершённый ход в конце файла (`assistant` с `tool_calls` без ответов инструментов —
  такой запрос API отклонит) отбрасывается с предупреждением;
- битый JSON не перезаписывается: агент сообщает об ошибке и предлагает `--new`.

Проверка с перезапусками (`--demo`): каждый шаг — новый процесс `python day7_memory.py --session demo_<время> "<запрос>"`,
общая у них только папка `memory/`.

| Запуск | Запрос | Что проверяется |
|---|---|---|
| 1 | «Который час сейчас в Токио? И сколько рублей стоят 150 долларов?» | вызваны `get_current_time` и `convert_currency`, история записана |
| 2 (перезапуск) | «Какое точное время, с секундами, вернул инструмент, когда я спрашивал про Токио? Инструменты не вызывай…» | инструменты не вызваны, в ответе ровно то время, которое вернул инструмент в запуске 1 (его не угадать) |
| 3 (перезапуск) | «Прибавь 10% к рублёвой сумме из моего первого вопроса.» | сумма из результата `convert_currency` запуска 1 попала в `calculator` или в ответ |

Для каждого шага ещё проверяется, что прошлые сообщения в файле не изменились и к ним добавились новые.
Результаты: `results/day7_<время>.md` (таблица: сообщений в истории до → после, вызовы, токены) и
`results/day7_<время>.json` (шаги и весь файл истории).

Выводы по прогону на `deepseek-v4.1-flash` (3/3 проверки) — в [`results/day7_conclusions.md`](results/day7_conclusions.md).

## День 8: работа с токенами

`day8_tokens.py` — агент из Дня 7 (`PersistentAgent`: те же инструменты, история в `memory/<сессия>.json`),
который после каждого хода показывает:

| Что | Откуда число |
|---|---|
| **текущий запрос** — сообщение пользователя | оценка до отправки (≈) |
| **запрос к модели целиком** — весь контекст: system, схемы инструментов, история, новое сообщение | оценка до отправки и точное `usage.prompt_tokens` после, с долей из кэша (`prompt_cache_hit_tokens`) |
| **вся история диалога** — сколько токенов в сохранённых сообщениях и сколько из них ушло в модель | оценка (≈) |
| **ответ модели** — с разбивкой на рассуждение и текст | `usage.completion_tokens`, `completion_tokens_details.reasoning_tokens`, `finish_reason` |
| **стоимость** хода и всего диалога, заполнение окна в % | по `usage` и ценам OpenCode Go; рядом — `usage.opencode.list_cost`, стоимость от самого провайдера (в прогоне совпали во всех 39 запросах) |

Точные числа есть только у API: токенизатора DeepSeek в проекте нет. Поэтому до отправки агент оценивает
запрос по составу символов (кириллица ~3 символа на токен, латиница ~4, цифры группами, знаки препинания
отдельно) и после каждого ответа калибрует оценку по настоящему `prompt_tokens`. Поправка сохраняется
в истории, так что калибровка переживает перезапуск. Оценка нужна, чтобы решить до отправки, поместится ли
запрос в окно.

Цены (OpenCode Go, за 1 млн токенов): вне пика $0.15 вход / $0.60 выход / $0.003 вход из кэша, в пик —
вдвое дороже (будни, 01:00–04:00 и 06:00–10:00 UTC). Окно `deepseek-v4.1-flash` — 1 048 576 токенов
(в документации «1M», точное число назвал сам API в ответе на запрос больше окна), ответ — до 384 000.

Переполнение окна (`--overflow`):
- `none` — отправлять историю как есть (так делал агент Дня 7). Что произойдёт, решает API;
- `truncate` — скользящее окно: в запрос не попадают самые старые ходы (целиком, вместе с вызовами
  инструментов), пока запрос и запас на ответ (`--reserve`, по умолчанию 1024, не больше четверти окна)
  не поместятся в окно. В файле истории остаются все сообщения, обрезается только то, что уходит в модель.

`--window N` эмулирует модель с окном N токенов по правилам настоящего API: запрос больше окна
отклоняется, на ответ остаётся не больше «окно − запрос» (`max_tokens`). Так переполнение можно показать
за доли цента, не отправляя миллион токенов.

```powershell
python day8_tokens.py                                   # чат со счётчиком (сессия tokens)
python day8_tokens.py --window 6000                     # чат в окне 6 000 токенов (эмуляция)
python day8_tokens.py --window 6000 --overflow truncate # то же со скользящим окном
python day8_tokens.py --demo                            # все сценарии + отчёт в results/
python day8_tokens.py --demo --scenarios short,long     # только выбранные
```

Команды чата: `/doc [N]` — отправить синтетический отчёт склада №N (~900 токенов, тот же, что в `--demo`;
без номера — следующий), `/tokens` — таблица ходов с ростом контекста и накопленной стоимостью,
`/window <N|real>` — сменить окно на ходу, `/overflow <none|truncate>`, `/history`, `/tools`, `/reset`, `/exit`.

Переполнение вживую (для видео), `python day8_tokens.py --new --window 5000`:

| Ввод | Что видно |
|---|---|
| `Запомни: номер моего заказа 7341-ZX, кодовое слово «бергамот». Ответь одним словом.` | первый ход: ~750 токенов, почти всё — system и схемы инструментов |
| `Который час в Токио?` | два запроса к модели за ход: вход считается дважды |
| `/doc` — повторять, пока не появится ❌ (3–4 раза) | окно заполняется (≈20 → 40 → 60 → 80%), вход растёт, а стоимость хода почти нет — работает кэш; затем запрос не помещается и отклоняется |
| `/tokens` | таблица: рост контекста и накопленная стоимость |
| `/overflow truncate`, затем `/doc` | ✂️ старые ходы больше не отправляются, кэш пропадает — ход дороже при меньшем контексте |
| `Напомни мой номер заказа и кодовое слово.` | факт выпал из окна — агент его не знает |
| `/window real`, затем тот же вопрос | вспомнил: история хранится целиком, обрезалось только то, что уходило в модель |

Сценарии `--demo`:

| Сценарий | Что в нём | Что проверяется |
|---|---|---|
| `short` — короткий диалог | 3 хода, два с инструментами | токены и стоимость на ход, всё без ошибок |
| `long` — длинный диалог | факт в 1-м ходе («номер заказа 7341-ZX, слово „бергамот“»), 10 синтетических отчётов склада по ~900 токенов с вопросом к каждому, в конце — вопрос о факте | контекст растёт каждый ход, факт помнит |
| `overflow` — переполнение, `none` | тот же диалог в окне 6 000 (эмуляция) + просьба о длинном ответе | ходы, которые не влезли, отклоняются; места под ответ всё меньше |
| `overflow` — переполнение, `truncate` | то же со скользящим окном | отказов нет, но факт из 1-го хода выпал из окна и забыт |
| `real` — больше настоящего окна | короткий ход → журнал на 1 000 строк (по нему считается, сколько токенов в строке) → журнал на ~1,05 млн токенов → короткий ход | что отвечает настоящий API на запрос больше 1M; что агент после этого жив |

Сценарий `real` отправляет один запрос примерно на 2,5 МБ текста (таймаут — 300 с). Отклонённый запрос
ничего не стоит; если бы сервер его принял, он обошёлся бы примерно в $0.16 (вне пика).

Результаты: `results/day8_<время>.md` — таблица сравнения сценариев и по каждому ходу: запрос ≈, история ≈,
вход (кэш), ответ (рассуждение), % окна, стоимость хода и нарастающим итогом, полоска роста контекста;
`results/day8_<время>.json` — то же плюс сырой `usage` каждого запроса.

Выводы по прогону на `deepseek-v4.1-flash` (5/5 сценариев) — в [`results/day8_conclusions.md`](results/day8_conclusions.md).

## День 9: сжатие истории

`day9_compression.py` — агент из Дня 8 (`TokenAgent`: те же инструменты, история в JSON, счётчик токенов
и стоимости), который отправляет в модель не всю историю. `CompressingAgent` собирает каждый запрос так:

| Часть запроса | Что в ней |
|---|---|
| системный промпт | как раньше, плюс блок «Краткое содержание начала разговора» с текущим summary |
| последние N сообщений | как есть, без изменений (`--keep`, по умолчанию 6) |
| текущий ход | сообщение пользователя и, если были, вызовы инструментов с результатами |

Как только за пределами этих N сообщений накопится `--chunk` несжатых сообщений (по умолчанию 10), перед следующим
ходом они вместе с прежним summary уходят отдельным запросом к модели-«сжимателю» (`temperature=0`), и summary
обновляется. Так summary пересобирается каждые 10 сообщений. Граница сжатия всегда проходит по началу хода,
поэтому вызов инструмента не отрывается от своего результата.

Где что хранится:
- `memory/<сессия>.json` — полная история, как в Днях 7–8. Сжимается только то, что уходит в модель,
  сами сообщения не удаляются;
- `memory/<сессия>.summary.json` — отдельно: текст summary, до какого сообщения истории оно доходит
  (`summarized_upto`) и журнал сжатий (какие сообщения, ≈ токенов до/после, `usage` и стоимость запроса к сжимателю).
  После перезапуска summary подхватывается; если оно не сходится с историей (файл правили руками),
  агент его не использует и сожмёт историю заново.

Стиль summary (`--style`):
- `facts` — структурированное резюме по разделам (участники, проект, сроки, бюджет, ограничения, решения).
  Имена, числа, даты и решения переносятся точно, изменившееся значение помечается: «бюджет: 5 млн (было 4 млн)»;
- `brief` — пересказ в 2–3 предложениях, как если просто попросить модель «сожми». Нужен для сравнения:
  показывает, какие детали теряются;
- `off` — без сжатия, вся история в каждом запросе (как в Дне 8).

```powershell
python day9_compression.py                       # чат со сжатием (сессия compress)
python day9_compression.py --new                 # начать заново (история и summary уходят в архив)
python day9_compression.py --keep 4 --chunk 6    # сжимать чаще
python day9_compression.py --style off           # тот же чат без сжатия
python day9_compression.py --summary-model <id>  # сжимать другой (например, более дешёвой) моделью
python day9_compression.py --demo                # сценарий в режимах off / facts / brief + отчёт в results/
python day9_compression.py --demo --modes off,facts
```

Команды чата: `/play [N]` — отправить следующие N реплик сценария (без числа — все оставшиеся),
`/probe` — задать 12 контрольных вопросов по деталям сценария, `/summary` — текущее summary и журнал сжатий,
`/context` — из чего состоит запрос (system, summary, сколько сообщений как есть, ≈ токенов против полной истории),
`/compress` — сжать сейчас всё за пределами хвоста, не дожидаясь порога, `/tokens`, `/history`, `/reset`, `/exit`.
После каждого хода агент показывает, что ушло в запрос, точный вход и вход «без сжатия» (оценка полной истории
в масштабе точного `prompt_tokens`), когда будет следующее сжатие и стоимость (ход, диалог и отдельно сжатие).

Ходы 6, 12, 13 — вопросы без новых деталей. С настройками по умолчанию (хвост 6, порог 10) сжатие происходит

детали ходов 1–10 есть только в summary, причём ходы 1–5 сжаты дважды (summary от summary), а бюджет должен
обновиться при втором сжатии. Деталь хода 11 остаётся в хвосте как есть — это контроль.

`--demo` проводит этот диалог в трёх режимах (`off`, `facts`, `brief`), каждый в своей сессии. Затем задаёт
12 контрольных вопросов. Каждый вопрос — отдельный запрос с контекстом агента после диалога. В историю вопросы
не попадают, поэтому ответ на один вопрос не подсказывает следующий. Ответ засчитывается, если в нём найдены
ключевые слова детали (например, «Арсений» и «Гладков», «2,7 млн»). Той же проверкой просматривается текст summary:
так видно, потерялась деталь при сжатии или модель не нашла её в summary.

Упавший запрос (после повторов) в сравнении помечается ⚠️ и в честный счёт «без ⚠️» не входит: агент откатывает
ход, который не прошёл, и названная в нём деталь до него просто не доходит. Если не прошёл контрольный вопрос,
проверить деталь нельзя. Повторы печатаются строкой ⏳, а по каждому режиму считаются запросы, повторы и отказы.

Результаты: `results/day9_<время>.md` — сколько деталей помнит каждый режим (с пометкой «в summary ✓/✗»),
расход токенов (вход за диалог и из кэша, вход и выход сжимателя, вход всего и изменение относительно `off`,
контекст последнего хода, вход на контрольный вопрос, стоимость), вход по ходам с отметками сжатий,
итоговое summary каждого режима и все ответы на контрольные вопросы; `results/day9_<время>.json` — то же
плюс сырые данные. Истории и summary прогона — `memory/day9_<режим>_<время>.json` и `.summary.json`.

Для видео, `python day9_compression.py --new`:

| Ввод | Что видно |
|---|---|
| `/play 8` | 8 реплик сценария: контекст растёт с каждым ходом, сжатия ещё нет |
| `/play 1` | 🗜 перед ходом сжимаются 10 сообщений (ходы 1–5): вход падает, рядом — сколько было бы без сжатия |
| `/summary`, `/context` | что сохранилось в summary; из чего теперь состоит запрос |
| `/play` | оставшиеся реплики |
| `/probe` | ещё одно сжатие и 12 контрольных вопросов: ✅/❌ по каждой детали |
| `/exit`, `python day9_compression.py --session v_brief --style brief`, `/play`, `/probe` | то же с пересказом — какие детали потерялись |
| `/tokens` | ходы, рост контекста и стоимость, отдельной строкой — сжатие |

Сравнение всех режимов одной таблицей — `python day9_compression.py --demo` (≈ 95 запросов к модели;
в конце печатается таблица «деталь × режим» и расход токенов).

Выводы по прогону на `deepseek-v4.1-flash` — в [`results/day9_conclusions.md`](results/day9_conclusions.md).
Если коротко: со структурированным summary агент помнит все 12 деталей, с пересказом — около половины сжатых. Вход за диалог
сжатие уменьшило на 22%, но из-за кэша провайдера диалог стал на 43% дороже. Проверка по ключевым словам
завышает счёт, если ответ отрицает деталь, но упоминает её слова: в выводах детали оценены вручную.

## День 10: стратегии управления контекстом

`day10_strategies.py` — агент из Дня 8 (`TokenAgent`: те же инструменты, история в JSON, счётчик токенов
и стоимости) с переключателем стратегии. `StrategyAgent` хранит полную историю, а стратегия решает только, что
уйдёт в модель:

| Стратегия | Что уходит в модель | Служебные запросы к модели |
|---|---|---|
| `sliding` — Sliding Window | системный промпт + последние N сообщений (`--keep`, по умолчанию 6); всё, что старше, отбрасывается | нет |
| `facts` — Sticky Facts | системный промпт с блоком «Факты из разговора» (ключ → значение) + последние N сообщений | 1 на каждое сообщение пользователя: обновить факты |
| `summary` — summary из Дня 9 | системный промпт с summary + несжатая часть истории | 1 раз в `--chunk` сообщений (по умолчанию 10): пересобрать summary |
| `full` — эталон | вся история, как в Днях 7–8 | нет |

Граница хвоста всегда проходит по началу хода: вызов инструмента не отрывается от результата.

**Sticky Facts.** Перед ответом на каждое сообщение пользователя служебный запрос (`temperature=0`) получает текущие
факты и новое сообщение. Модель возвращает только изменения: `{"set": {"бюджет": "2,7 млн ₽ (было 2,4 млн ₽)"},
"delete": []}`. Слияние делает код, поэтому модель не может «потерять» старый факт, переписывая весь блок.
Хранятся имена и роли, названия, цель, числа, суммы, сроки, ограничения, предпочтения, решения и договорённости.
Изменившееся значение записывается вместе со старым. В запрос извлечения идут только сообщения пользователя:
так в факты не попадают советы ассистента (в Дне 9 summary путало их с решениями).
Если запрос фактов не прошёл, агент всё равно отвечает, а пропущенное догоняет в следующем ходе. Если не прошёл
сам ход, факты, извлечённые из него, откатываются вместе с историей.

**Переключение** (`/strategy <имя>` или `--strategy`) ничего не теряет: состояние стратегий догоняется лениво.
Включили факты на середине диалога — первый же служебный запрос учтёт все пропущенные сообщения пользователя;
summary сожмёт всё, что накопилось за хвостом. `/context` показывает, сколько весил бы запрос на каждой стратегии.

**Ветвление.** `/checkpoint <имя>` сохраняет снимок: историю и состояние всех стратегий (факты, summary).
`/branch <имя> [checkpoint]` создаёт ветку от снимка (без checkpoint — от текущего места) и переключается на неё,
`/switch <ветка>` переключает, `/branches` рисует дерево. У каждой ветки своя история, свои факты и своя сессия
у провайдера, поэтому ветки продолжаются независимо. Всё лежит в `memory/day10/<сессия>/`:

| Файл | Что в нём |
|---|---|
| `branches.json` | текущая ветка; ветки — от какой ветки и какого checkpoint отходят; checkpoints |
| `<ветка>.json` | история ветки (формат Дня 7) |
| `<ветка>.state.json` | текущая стратегия и состояние всех стратегий: факты, summary, журнал служебных запросов с `usage` и стоимостью |
| `checkpoints/<имя>.json` | снимок: история и состояние стратегий в момент checkpoint |

```powershell
python day10_strategies.py                            # чат (сессия strategies, стратегия facts)
python day10_strategies.py --new                      # начать заново (папка сессии уходит в архив)
python day10_strategies.py --strategy sliding --keep 4
python day10_strategies.py --helper-model <id>        # факты и сжатие — другой (например, дешёвой) моделью
python day10_strategies.py --demo                     # сценарий Дня 9 на всех стратегиях + ветвление, отчёт
python day10_strategies.py --demo --modes sliding,facts --no-branches
python day10_strategies.py --demo --modes none        # только проверка ветвления
```

Команды чата: `/strategy [имя]`, `/play [N]` — следующие N реплик сценария Дня 9, `/probe` — 12 контрольных вопросов,
`/facts`, `/summary`, `/context`, `/compress` — сжать summary сейчас, `/checkpoint <имя>`, `/branch <имя> [checkpoint]`,
`/switch <ветка>`, `/branches`, `/tokens` (ходы плюс служебные запросы отдельной строкой), `/history`, `/reset`, `/exit`.
После каждого хода видно, из чего состоял запрос (факты / summary / сколько сообщений как есть, сколько отброшено),
точный вход, сколько было бы со всей историей, служебные запросы хода и стоимость.

### Сравнение на сценарии Дня 9

`--demo` берёт диалог и список деталей из Дня 9: 13 реплик, 26 сообщений с ответами и 12 деталей (имя, название,
числа, сроки, бюджет, ограничение, решения). Диалог проводится на каждой стратегии в своей сессии, с одинаковым хвостом
в 6 сообщений. Затем контекст готовится, как перед следующим ходом, и задаются 12 контрольных вопросов.
Каждый вопрос — отдельный запрос с контекстом стратегии, в историю он не попадает. Ответ засчитывается, если в нём
есть ключевые слова детали. Ответ, который содержит слова, но звучит как отрицание («не упоминалось»), помечается ❔ —
в Дне 9 такие ответы завышали счёт. Для каждой детали видно, где она была на момент вопроса: в хвосте, в фактах,
в summary или отброшена.

Сравнивается:
- **детали** — сколько из 12 помнит агент;
- **токены** — вход за диалог и из кэша, вход и выход служебных запросов, вход всего, контекст последнего хода,
  вход на контрольный вопрос, стоимость (ходы + служебные);
- **сложность** — строк кода класса стратегии и его помощников (без пустых строк, комментариев и docstring; считает
  сам скрипт через `ast`), размер служебного промпта и число вызовов модели на ход.

Затем `--demo` проверяет ветвление на Sticky Facts. В `main` проходят 4 хода сценария (имя, проект, пекарни,
срок, бюджет 2,4 млн), после чего ставится checkpoint `after-budget`. От него создаются две ветки:
- `growth` — бюджет вырос до 2,7 млн, но демо инвесторам нужно показать до 20 февраля (реплика 9 из Дня 9);
- `cut` — бюджет урезали до 1,9 млн, зато релиз сдвинули на 4 апреля.

Агент переключается между ветками и в каждой задаёт один и тот же вопрос: «какой бюджет и срок релиза?». Каждая ветка
должна назвать своё и не упомянуть значения другой ветки (утечка). Затем после переключения задаются вопросы: имя
пользователя (общая часть, должны знать обе ветки) и дата демо (знает только `growth`).

Результаты: `results/day10_<время>.md` — таблица «стратегия → деталей сохранено / токены / сложность», детали по
стратегиям с пометкой, где деталь хранилась, расход токенов, вход по ходам с отметками служебных запросов, итоговые
факты и summary, ветвление по шагам и факты каждой ветки, все ответы; `results/day10_<время>.json` — то же плюс
сырые данные. Истории прогона — `memory/day10/demo_<время>/compare/` и `.../branches/`.

Для видео, `python day10_strategies.py --new`:

| Ввод | Что видно |
|---|---|
| `/play 6` | факты 📌 обновляются после каждой реплики, вход растёт медленно: старые сообщения не уходят |
| `/facts`, `/context` | блок фактов; сколько весил бы запрос на каждой стратегии |
| `/checkpoint cp1`, `/branch growth cp1`, `/play 4` | ветка от checkpoint продолжает сценарий (бюджет 2,7 млн) |

Сравнение всех стратегий одной таблицей — `python day10_strategies.py --demo` (≈ 165 запросов к модели, ~30 минут).

Выводы по прогону на `deepseek-v4.1-flash` — в [`results/day10_conclusions.md`](results/day10_conclusions.md).

Окно и факты вдвое уменьшают запрос на вопрос, но диалог с ними вдвое дороже полной истории: сдвигающийся контекст
сбивает кэш провайдера, а без истории модель отвечает длиннее. Факты сохранили все параметры, но одну деталь испортили
«обновлением» (37 пекарен → 38). Ветки от checkpoint независимы: все 6 проверок прошли. Пока история помещается
в окно и кэшируется, выгоднее отправлять её целиком; дальше — факты для параметров и summary для хода обсуждения.

## Публикация результатов дня

Публикация делается через Claude по промпту [`tasks/PUBLISH_PROMPT.md`](tasks/PUBLISH_PROMPT.md).
Коммит в `main` и ветка `day_<N>` (N — сквозной номер дня) создаются в этой папке.
Старые ветки `week_<W>/day_<D>` (дни 1–6) оставлены ради внешних ссылок; их дубликаты — `day_1` … `day_6`. Затем коммиты переносятся bundle-файлом
в облачное окружение Claude, у которого есть доступ к GitHub, и отправляются оттуда одной атомарной операцией:
`main` и ветка дня уходят вместе или не уходят вовсе. На GitHub попадают ровно те же коммиты, что и здесь.

Перед коммитом проверяется:
- текущая ветка `main`, нет незавершённого merge/rebase и lock-файлов;
- локальный `main` не отстал от GitHub;
- ветки дня ещё нет ни локально, ни на GitHub;
- в коммит не попадают `.env`, ключ из `.env`, `.venv/`, бандлы и файлы больше 20 МБ.

После push проверяется, что `main` и ветка дня на GitHub указывают на новый коммит,
и эта папка подтягивает их состояние (`main...origin/main` без расхождений).
Правки вне дня (инструменты, README, промпты) публикуются так же, но только в `main`.
