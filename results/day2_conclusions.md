# Неделя 1 · День 2 — Формат ответа: выводы

Модель: `deepseek-v4.1-flash` (OpenCode Go). Запрос во всех вариантах один:
«Посоветуй 3 языка программирования для начинающего бэкенд-разработчика и объясни выбор».
Код: `day2_format.py`. Сырые ответы: `results/day2_*.json`.

## Сводка по трём прогонам

Учтены только ответы, которые дошли (таймауты отдельно — см. ниже).

| Вариант | `json.loads` | Прошёл схему | Как ломается |
|---|---|---|---|
| Без ограничений | 0/4 | 0/4 | Markdown-текст ~1800 токенов, `JSONDecodeError` на первом символе |
| Формат описан в промте | 4/4 | 4/4 | не сломался — но ничем не гарантирован |
| Формат + `max_tokens=60` | 0/7 | 0/7 | **пустой** `content`: все 60 токенов ушли на рассуждение |
| Формат + `max_tokens=1500` | 2/2 | 2/2 | не сломался — лимит больше реального ответа (~350) |
| Формат + stop `<END>` | 3/8 | 3/8 | 1-й прогон: 5/5 пустых (20–34 токена); 3-й прогон: 3/3 OK |
| JSON mode (`json_object`) | 5/5 | 5/5 | не сломался |
| Строгая JSON Schema | 5/5 | 5/5 | не сломался |
| Схема + `max_tokens=60` | 0/7 | 0/7 | JSON **обрезан** посередине (`Unterminated string`) или пуст |
| Схема + `max_tokens=1500` | 2/2 | 2/2 | не сломался |

Отдельно: 5 из 35 запросов первого прогона упали по таймауту 60 с — нестабильность провайдера, не формата.

## Что ломается и на чём

1. **Без ограничений** — код распарсить не может вообще: модель отвечает статьёй в Markdown,
   и ответ в 5 раз длиннее, чем с форматом.

2. **Описание формата в промте** на этой модели сработало 4/4, но это поведение модели, а не контракт:
   формат ничем не проверяется на стороне API, и на другой модели/температуре появятся
   ```json-обёртки и текст вокруг (их скрипт ловит отдельной колонкой «после чистки»).

3. **`max_tokens` не управляет форматом — он только обрывает генерацию.** У reasoning-модели
   это проявляется неочевидно: лимит считается вместе со скрытым рассуждением, поэтому при
   `max_tokens=60` все 60 токенов ушли на рассуждение (`reasoning_tokens=60`), а `content` пустой.
   Со строгой схемой модель рассуждение пропускает (`reasoning_tokens=0`) и честно пишет JSON —
   но обрывается на середине строки: `JSONDecodeError: Unterminated string`.
   **Схема не защищает от обрезки.** (В первом прогоне схема + 60 давала не обрезанный, а пустой
   ответ — как без схемы.) С лимитом 1500 оба варианта — 4/4.

4. **Stop sequence нестабилен у reasoning-модели.** Маркер `<END>` упомянут в инструкции, и модель
   повторяет его в рассуждении (видно в `reasoning`). В первом прогоне все 5 ответов оборвались на
   20–34 токенах с `finish_reason=stop` и пустым `content` — stop сработал раньше ответа.
   В третьем прогоне рассуждение тоже содержало `<END>`, но stop применился только к ответу — 3/3 OK,
   а сам маркер из ответа срезан. Один и тот же запрос дал 0/5 и 3/3: на stop sequence с маркером
   из промта полагаться нельзя.

5. **JSON mode и строгая JSON Schema — единственные варианты без единой поломки (10/10)**
   при достаточном лимите. JSON mode гарантирует синтаксис, схема — ещё и структуру.

Наблюдение: первый и третий прогоны различаются сразу в двух местах (stop и схема + лимит) —
похоже, что за одним id модели у провайдера в разное время отвечают бэкенды с разной обработкой
рассуждения. Это ещё один довод не полагаться на поведение модели, а проверять ответ кодом.

## Правила, которые из этого следуют

- Нужен машиночитаемый ответ → `response_format` со строгой схемой (или хотя бы `json_object`)
  и всё равно проверка схемы в коде.
- Всегда проверять `finish_reason`: `length` = ответ обрезан, парсить нечего.
- `max_tokens` ставить с запасом на рассуждение, а не «под размер ответа».
- Stop sequence не упоминать в промте reasoning-модели или не использовать для обрезки формата.
